## 六、针对性解决失败模式

[13:01] 清理之后，我们可以看到现在有两个测试用例持续通过，但我们有三个关键失败模式：按比例计算、账单错误和热点数据。

### 6.1 热点数据问题

[13:30] 首先是热点数据问题，问题是：我的无限套餐有多少热点数据。

[13:37] 我们期望模型做的是直接说明客户拥有的热点数据量。

[13:44] 这个案例之所以有点复杂，是因为我们处理的客户测试用例使用的是旧套餐（Legacy Plan）。

[13:52] 实际上当前的政策不适用于他们，所以如果我们看看实际测试用例中发生了什么，我们传给 Prompt 的客户数据。

[14:05] 包含了客户拥有的热点数据量，他们有 5GB，但他们也有一个祖父套餐（Grandfather Plan）。

[14:13] 我们看到模型实际上告诉客户的是：一般的无限套餐包含 4GB，但由于你使用的是旧套餐，你应该自己去查看。

[14:29] 让我们看看 Prompt，了解为什么模型将这个问题推给客户账户 URL，而不是自己提供信息。

[14:51] 如果我们从原文阅读，它说：我们最近更改了套餐，政策文档显示当前套餐数据，使用祖父套餐的客户有不同的费率，永远不要给客户错误的套餐详情，而是引导他们到 URL。

[15:06] 很明显，这条指令——永远不要给客户错误信息——是机器人一直在优化的指令。

[15:16] 你们可能会认出这非常类似于你们可能为之前使用的模型引入的补丁，用于避免模型给客户提供错误的套餐信息。

[15:32] 随着我们模型的演进，它们在指令遵循方面变得更好，所以像这样的指令很可能已经变得多余，实际上被过度遵循了。

[15:46] 所以我们要告诉模型的是：给出一个平衡的观点，说明使用祖父套餐的客户有不同的配额，但这已经包含在给定的客户信息中，那是准确的真相来源。

[16:01] 在这里运行评估，我们希望现在能解决热点数据用例的所有测试用例。我正在实时运行，所以可能会有一些变化，但我们看到现在所有测试用例都清楚地通过了。

[16:22] 我们学到了什么？我们非常担心幻觉或编造事实和数字，但实际上相反的情况也可能发生——模型可能会扣留它实际上有权限访问的信息。

[16:41] 我们看到这很可能是我们为之前的模型引入的补丁的结果，我们可以遵循的最佳实践是使用版本控制。

[16:52] 每当我们在 Prompt 中进行防御性更改时，我们要追踪引入这些更改的原因。有时它们是必要的，但在未来，这类更改可能会产生不良影响，这样我们可以回溯它们。

### 6.2 按比例计算问题

[17:12] 下一个失败的测试用例是这个按比例计算，客户问：如果我升级到 30GB 套餐，我的下一份账单会是多少？我们希望模型进行一些计算，并准确返回下一份账单会是多少，而不是给出某种失败的输出，这正是我们现在看到它做的。

[17:39] 如果我们看模型返回的内容，它显然在推理，做了一些心算，但它并没有真正给客户一个具体的答案，我不会依赖这个来准确给客户回复。

[17:55] 如果我们看 Prompt 来了解如何修复这个问题，在原始 Prompt 中我们可以看到给它的所有指令是告诉它：永远不要给客户模糊的答案。

[18:20] 关键是要正确计算任何按比例分摊的金额。现在，当我们没有给模型实际做好工作的能力时，告诉它做好工作并没有特别大的帮助。

[18:36] 我们想避免模型做心算，所以我们要引入的是给模型一个工具，在 Prompt 中说：每当你进行任何计算时，请使用 calculate_pro ration 工具来做。

[18:50] 为了引入那个工具，我们需要在 API 中引入它，告诉模型你可以访问这个工具。我们需要定义工具模式（Tool Schema），告诉模型这个工具做什么以及何时使用它。

[19:06] 然后我们需要实际实现工具，即它应该如何进行计算。

[19:15] 再次运行评估。

[19:22] 我们可以看到所有测试用例现在都通过了，它显然在后台使用工具进行了计算，并返回了正确的响应。

[19:39] 这里要记住的关键教训是：指令不会增加能力。告诉模型正确计算很关键，并不会让它更擅长心算。

[19:53] 正确的方法是给它一个工具，总体上给它推理更难问题的能力，并使用工具来可靠地执行它们。

### 6.3 账单错误升级问题

[20:06] 现在我们还有一个最后失败的测试用例需要解决，就是这个账单错误。

[20:15] 在这个场景中，存在账单冲突，我们真正希望的是 Agent 将此升级给人工处理。

[20:24] 我们看到它做的是试图向客户解释可能的原因。

[20:34] 它试图自己诊断问题。

[20:39] 为了修复这种行为，让我们再看看 Prompt 中告诉了它什么。

[20:55] 我们在初始指令中看到它说：避免升级或转交给客服专员，除非绝对必要，因为这大约花费 8 美元，会计入我们团队的快速解决合同指标。

[21:09] 这只给了故事的一面，对吧？我们告诉它升级的成本，但没有告诉它好处，这意味着它会再次过度优化为不升级。

[21:23] 其次，我们在评估中定义的我们希望模型做的（进行升级）与我们在 Prompt 中实际告诉它做的之间存在明显的冲突。

[21:33] 相关的修复是给它故事的两面，说：升级一个案例需要花费 8 美元。

[21:46] 但实际上，如果你弄错了，那将花费你退款以及客户信任。

[21:56] 我们再次观察到模型如何优化目标，这类指令是一种常见的指令，与我们之前看到的非常相似。

[22:08] 我们不希望它过度优化某种类型的行为，但这种指令可能会被不同代际的模型以非常不同的方式遵循。

[22:18] 特别是随着模型变得更加智能，我们需要记住说明权衡的两面，因为我们的模型自己在做这些权衡方面也变得更好。

[22:32] 让我们回到评估，运行我们最后的测试用例，我们应该看到所有评估现在都正确通过了。

[22:52] 总的来说，我们研究了应用通用清理原则，这如何为 Prompt 提供初始提升，确保我们删除任何多余的指令，这些指令最初是作为之前模型行为的补丁引入的。

[23:07] 确保我们给它工具来可靠地执行某些任务。

## 核心要点总结

### Prompt 维护最佳实践

1. **建立评估套件**：包含控制用例、边缘用例和能力边界用例
2. **结构化 Prompt**：使用 XML tags 分离角色、指南、政策、语气等
3. **清理遗留补丁**：删除针对旧模型的冗余指令
4. **创建输出契约**：定义清晰的输出格式，使用 Stop Sequence

### 常见反模式

- 告诉模型它是人类
- 复制粘贴网站内容到 Prompt
- 所有指令混在一个大段落
- 过度防御性的"永远不要"指令
- 告诉模型做好工作但不给工具

### Agent 构建策略

- 简单任务：小模型 + 好 Prompt
- 复杂推理：大模型 + Extended Thinking
- 高可靠性：生成-评估-修复循环

### 关键教训

- **指令不增加能力**：需要计算时给工具，而不是告诉它"正确计算"
- **说明权衡的两面**：不只说成本，也要说收益
- **版本控制**：追踪防御性更改的原因
- **模型可能扣留信息**：不只是幻觉，过度优化也可能导致信息扣留
